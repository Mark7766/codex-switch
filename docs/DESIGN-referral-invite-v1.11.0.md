## 1. 背景与定位

### 1.1 为什么现在做？

| 时机         | 说明                                                            |
| ------------ | --------------------------------------------------------------- |
| 产品价值到位 | v1.10.0 插件功能 + v1.11.0 自动更新，产品已经有"值得推荐"的底气 |
| 零成本       | 下载走 CDN/Server，不增加额外成本                               |
| 自然增长时机 | 插件和自动更新两个重磅功能上线，是最好的推荐窗口                |

### 1.2 定位原则

> **产品价值是增长的核心，邀请机制只是"放大器"，不是"驱动力"。**

- ❌ 不做积分、不做排行榜、不做强制邀请
- ❌ 不做"邀请 3 人解锁功能"（破坏信任）
- ✅ 降低分享门槛——用户觉得好用，顺手就能推荐给朋友
- ✅ 让被邀请的人感受到"朋友推荐"的温度，而不是广告

## 2. 核心设计

### 2.1 一句话概述

用户点一下按钮 → 复制一段推荐语 + 安装指南链接 → 粘贴到微信/飞书/朋友圈 → 朋友打开指南，按步骤安装。Server 记录邀请关系，Admin 后台可看到增长数据。

### 2.2 用户故事

> **小张**用 Codex Switch 两周了，终于不用翻墙就能用上 Codex 和 Claude。同事问他"你怎么在国内用上 Codex 的？"他打开 Codex Switch，侧边栏底部「💚 推荐给朋友」一直在那里——之前他没在意，现在正好需要。点了一下，toast 提示已复制，粘贴到微信发给同事。同事点链接打开安装指南，一步步装好了。小张完全没觉得自己在"拉新"——他只是在回答同事的问题。

## 3. 分享激励：让推荐成为一件"温暖的事"

### 3.1 业内标杆案例

分享不能只靠便利性——用户需要一个**情感驱动**。以下是业内最成功的"非金钱激励"案例：

**案例一：GitHub 贡献热力图**

```
     Jan Feb Mar Apr May Jun
  Mon ░░▒▒▓▓██▓▓▒▒░░
  Tue ░░░▒▒▓▓██▓▓▒▒░
  Wed ░░░░▒▒▓▓██▓▓▒▒
  ...
```

这不是数据看板，这是**身份**。每个绿色方块都在说："这一天，我在这里创造了东西。"用户免费为 GitHub 贡献代码，GitHub 回报的不是钱——是**不可替代的归属感**。

> 启示：给用户一个"我属于这里"的印记，比任何物质激励都持久。

---

**案例二：Figma Community — "Remix" 计数**

```
  ┌─────────────────────────┐
  │  Design System v2.0     │
  │  by @mengto              │
  │                         │
  │  ❤️ 2.3k  🔄 846 Remix  │
  └─────────────────────────┘
```

Figma 不给钱、不给积分。只给两个数字——喜欢数和复用数。设计师因为自己的作品被"Remix"了 846 次而感到**骄傲**。这是纯粹的社会认同。

> 启示：用户在乎的不是钱，是"有多少人因为我而受益"。

---

**案例三：线性 (Linear) 的"Changelog 署名"**

```
  Changelog — May 2026

  ✨ New: Auto-update
  Built by @karri, @tommoor, @tuomas
  Shipped 2026-05-15
```

每一条功能更新都标注了开发者名字。用户看到的不只是新功能，是**一群具体的人在为他们工作**。信任感就是这样建立起来的。

> 启示：把"产品"变成"人"。用户不是一个工具的用户，而是一个社区的成员。

---

**案例四：Arc 浏览器的"成员卡"**

```
  ┌──────────────────────┐
  │  Arc Member          │
  │  #4,217              │
  │  Joined October 2023  │
  └──────────────────────┘
```

Arc 用了一个极其简单的方法让用户产生归属感：**加入日期 + 序号**。"我是第 4217 个用 Arc 的人"——这句话本身就变成了社交货币。用户自发在社交媒体晒自己的号码。

> 启示：给用户一个"编号"，他们就会自己传播。

---

**案例五：Product Hunt Maker 主页**

```
  @levelsio
  ─────────────
  🏆 Maker of the Year 2023
  🦄 12 Featured Products
  👥 8,400 Followers

  Ships every week. Builds in public.
```

Product Hunt 的 Maker 主页是社交身份的**集大成者**：徽章、数字、称号。Maker 们在上面获得的社会认同，驱动着他们年复一年地创作和分享。

> 启示：把"分享者"变成"创作者"，把"推荐"变成"贡献"。

### 3.3 Codex Switch 的激励设计

从中提炼出三个适合我们的机制。**不做积分、不做排行榜、不做物质激励**。

**激励一："早期成员"——身份标签**

```
┌─ 侧边栏 ─────────────────────┐
│  Codex Switch                │
│  让 Codex 连上 DeepSeek       │
│  ─────────────────────────── │
│                              │
│  🏠 主面板                   │
│  ⚙️ 设置                     │
│  🔌 插件                     │
│  📜 日志                     │
│                              │
│  ─────────────────────────── │
│  🎖 早期成员                  │  ← 仅 v1.11.0 前安装的用户展示
│     加入于 2026 年 3 月        │
│     15 位朋友通过你加入         │
│  ─────────────────────────── │
│  💚 推荐给朋友                │
│  和 327 位朋友一起使用       │
│  ─────────────────────────── │
│  🟢 代理 运行中               │
└──────────────────────────────┘
```

**为什么放在侧边栏而非 Settings**：Settings 是功能配置区——放身份铭牌就像是把护照放在工具箱里，找得到但语境完全不对。身份应该放在"门厅"——侧边栏是用户每次打开应用视线扫过的地方。对标 Apple Music 侧边栏顶部的个人头像区域、Xcode 左侧导航栏底部的账户入口。信息在，但从不叫嚷。

- "早期成员"是**定性标签**，不是数字排名——v1.11.0 发布前安装的用户永久拥有，之后安装的用户不显示这行
- "加入于"日期取自本地 `lifetimeFirstStartAt`（已有字段），不需要 Server
- "通过你加入"的数量调 `GET /api/v1/referral/stats?client_id=xxx`
- 三行紧凑，和分享入口、社区计数、代理状态形成一个**自然的侧边栏底部区域**——用户信息→社交→系统状态，信息层级清晰

**激励二："感谢你让这一切发生"——推荐者致谢**

侧边栏「💚 推荐给朋友」点击后，toast 文案不是"已复制"——而是：

```
┌──────────────────────────────────┐
│                                  │
│     💚                           │
│  感谢你把 Codex Switch            │
│  推荐给朋友                       │
│                                  │
│  每多一个人用上 Codex 或者 Claude，         │
│  都是因为你。                     │
│                                  │
│     [ 📋 复制推荐语 ]             │
│                                  │
└──────────────────────────────────┘
```

这不是功能弹窗，是**致谢信**。用户分享不是因为"复制按钮很方便"——而是因为"原来我帮到了别人"。

**激励三："我们在一起"——社区计数**

侧边栏底部，代理状态上方：

```
┌─ 侧边栏 ─────────────────────┐
│  ...                          │
│  📜 日志                      │
│                               │
│  💚 推荐给朋友                 │
│  和 327 位朋友一起使用        │  ← 不写"已有"，写"和…一起"
│  ──────────────────────       │
│  🟢 代理 运行中               │
└──────────────────────────────┘
```

文案策略：不是"已有 327 个用户"——是"**和** 327 位朋友**一起**"。从冷冰冰的数据变成温暖的共同体。"你"也是这 327 个中的一员。

### 4.1 分享者视角

侧边栏底部，代理状态上方，常驻一行轻量入口：

```
┌─ 侧边栏 ─────────────────────┐
│  ...                          │
│  📜 日志                      │

│  ──────────────────────       │

└──────────────────────────────┘
```

点击后：

```
✅ 已复制到剪贴板

粘贴到微信 / 飞书 / 朋友圈即可：

---
让 AI 编程触手可及

不用翻墙，不用注册海外账号，
Codex Switch 帮你突破网络限制，
在国内流畅使用 Codex 和 Claude。

✅ 无需翻墙，本地安全
✅ 接入 DeepSeek，免费快速
✅ 一键安装 173 个精选插件

上手指南：https://www.codexswtich.cloud/guide?ref=a1b2c3d4e5f6g7h8
---

（分享链接中包含你的邀请码，平台会记录你帮助了多少朋友）
```

### 4.2 被邀请者视角

被邀请者点开链接 → 看到安装指南页面 → 按步骤选择工具、安装配置、装插件。**全程无感知被"邀请"**——他们只是在朋友的推荐下找到了一个贴心的指南。

唯一不同的是：链接带了 `?ref=` 参数。Server 记录访问并匹配归属，但对用户完全透明。

> 不做"注册"、不做"填写邀请码"——被邀请者不需要任何额外操作。

### 4.3 邀请码机制

```
每个安装已有唯一 clientId（v1.7.0，16 位 hex，如 a1b2c3d4e5f6g7h8）
  ↓
直接用完整 clientId 作为 ref（不截断、不映射）
  ↓
分享链接：https://www.codexswtich.cloud/guide?ref=a1b2c3d4e5f6g7h8
  ↓
Server 安装指南页记录 ref → 用户按指南完成安装 → 归属匹配
```

> **为什么用完整 clientId 而不是前 6 位**：6 位前缀反查需要 `LIKE 'abc123%'` 全表扫描，数据量大了会退化；且两个不同 clientId 可能共享前 6 位前缀（碰撞概率低但不为零）。完整 clientId 是精准主键查詢，零碰撞、零扫描。

## 5. Server 端设计

### 5.1 归属机制：IP + 时间窗口匹配

Electron 桌面应用**无法**从网页链路中读取 `?ref=` 参数——用户流程是 点链接 → 打开安装指南 → 按指南下载安装 → 启动应用。到启动应用时 `?ref=` 早已丢失。

正确的归属链路是**纯 Server 端推断**，客户端零改动：

```
时间线 ──────────────────────────────────────────────────────▶

T1: 用户 A 点分享 → 朋友打开 GET /guide?ref=clientId_A
    Server 记录：page_events { path: "/guide", ref: clientId_A, ip: IP_Y }

T2: 用户 B 按指南操作 → 下载 Codex Switch → 安装 → 首次启动
    → POST /api/v1/telemetry { event: "app_start", client_id: clientId_B, ... }
    此时 Server 检测到 clientId_B 首次出现（is_first_launch = true）

T3: 定时任务（每小时跑一次）：
    对每个 is_first_launch 的 client_id：
      1. 找到该 client_id 首次 app_start 的 IP → IP_Z
      2. 在时间窗口（app_start 前 7 天内）反查 page_events：
         WHERE ip_hash = hash(IP_Z) AND path = '/guide' AND ref IS NOT NULL
         ORDER BY created_at DESC LIMIT 1
      3. 找到 ref → 这就是邀请者 clientId → INSERT INTO referrals
      4. 找不到 → 自然安装，不需要记录
```

**关键约束**：

| 约束         | 说明                                                     |
| ------------ | -------------------------------------------------------- |
| 时间窗口     | 指南页访问在安装前 7 天内才算归属（排除巧合同 IP）       |
| IP 去伪      | 同一 IP 短时间多次安装 → 只取最近一次带 ref 的指南页访问 |
| 定时批量     | 每小时跑一次，不实时（避免影响 app_start 写入性能）      |
| 客户端无感知 | 不需要客户端传 ref，现有 app_start 遥测已包含 IP         |

### 5.2 分享链接追踪

`/guide` 是现有 portal 路由（`portal/router.py`），只需在路由函数中增加 3 行：

```python
ref = request.query_params.get("ref")
if ref:
    # 写入 page_events，ref 字段标记邀请者
```

> `?ref=` 参数对指南页面完全透明——页面 UI 不变，仅在 Server 端静默记录。不带 ref 的访问也正常工作。**不需要新建 `shortlink.py`**。

### 5.3 核心表：`client_registry` — 客户端永久编号

为每个客户端分配一个**永久的、自增的编号**。编号是身份标识，不是排名。对标 Arc 成员卡（`#4217`）。

```sql
CREATE TABLE client_registry (
    id INTEGER PRIMARY KEY AUTOINCREMENT,   -- client_number，永久不变
    client_id TEXT UNIQUE NOT NULL,         -- 现有 16 位 hex
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

**编号分配**：

- **历史用户回填**（v1.11.0 上线时执行一次）：按首次 `app_start` 时间排序插入，最早的用户拿到 #1
- **新客户端**：每次 `app_start` 时 `INSERT OR IGNORE INTO client_registry (client_id) VALUES (?)`——已存在的跳过，新客户端自动拿到下一个编号

**并发控制**：SQLite 单写者模型下 AUTOINCREMENT 天然串行。FastAPI async session + SQLite 写锁保证不会产生重复编号。不需要额外加锁。

### 5.4 新增端点：客户端身份信息

`GET /api/v1/client/{client_id}/profile`

**Response**：

```json
{
  "code": 0,
  "data": {
    "client_number": 127,
    "is_early_member": true,
    "joined_date": "2026-03-15",
    "invite_count": 15
  }
}
```

| 字段              | 来源                                      | 说明                                        |
| ----------------- | ----------------------------------------- | ------------------------------------------- |
| `client_number`   | `client_registry.id`                      | 永久编号                                    |
| `is_early_member` | `client_registry.id <= 回填最大编号`      | v1.11.0 前安装 → `true`，之后安装 → `false` |
| `joined_date`     | `telemetry_events` 最早 `app_start`       | 首次启动日期                                |
| `invite_count`    | `referrals` 表 `COUNT(inviter_client_id)` | 通过你安装的人数                            |

**`is_early_member` 判定逻辑**：历史回填时 `client_registry` 会一次性获得 `[1, N]` 的编号（N = 回填时的总用户数）。`id <= N` 就是早期成员，后续新用户编号从 `N+1` 开始自然就是 `false`。

**缓存**：1 小时。编号、早期成员标签、加入日期永久不变，仅 invite_count 随邀请增长变化。

> 相比单独查询"邀请了多少人"，这个端点一次返回完整身份信息——客户端 Settings 身份铭牌只需调一个接口。

## 6. 客户端设计

### 6.1 设计哲学：Apple 式的"不经意"

> Apple 不会在 Dock 上放一个"告诉朋友"按钮。但 AirDrop 的分享图标无处不在——菜单栏、Finder 右键、照片 App 的工具栏。随时可用，但从不打扰。

Codex Switch 的分享不应该是一个"功能板块"，而应该是一个**自然流露的动作**。用户在某一个瞬间觉得"这东西真不错"——那一刻，分享入口刚好在视线里。

**一个原则：用户不需要寻找，但也不会被骚扰**。

### 6.2 侧边栏底部（常驻入口）

侧边栏底部已有代理状态指示器。在它上方加一行，保持同样的轻量风格：

```
┌─ 侧边栏 ─────────────────────┐
│                              │
│  🏠 主面板                   │
│  ⚙️ 设置                     │
│  🔌 插件                     │
│  📜 日志                     │
│                              │
│  ─────────────────────────── │
│  💚 推荐给朋友               │  ← 仅一行文字 + 图标
│  ─────────────────────────── │
│  🟢 代理 运行中              │
└──────────────────────────────┘
```

**为什么放这里**：

- 侧边栏是用户每次切换页面都会扫过的地方，**视线必然经过**
- 不占主内容区，不打断用户工作流
- 和代理状态指示器同级，轻量、不喧宾夺主
- 对标：Apple 菜单栏图标——始终在，但从不抢注意力

点击后行为：直接复制推荐语到剪贴板 + 顶部浮出 toast "✅ 已复制，粘贴给朋友即可"（2 秒自动消失）。不弹窗、不跳转。

### 6.3 不做什么

| ❌ 不做                | 原因                                   |
| ---------------------- | -------------------------------------- |
| Dashboard 内容区加卡片 | 用户来看代理状态，不是来看广告的       |
| 弹窗 / Modal           | 打扰用户当前任务，Apple 从不这么做     |
| HeaderBar 加按钮       | 那是操作区（帮助按钮），不是推广区     |
| 首次启动弹引导         | 用户还没体验到价值就让他推荐，虚假转化 |

### 6.4 分享文案

```
🤖 推荐你一个工具：Codex Switch

如果你用 Codex 或 Claude Desktop，
装不上插件、连不上 DeepSeek——
这个工具能一键搞定。

✅ 173 个 Codex 插件国内高速下载
✅ Claude Desktop 扩展支持
✅ 自动更新，零配置

下载：https://www.codexswtich.cloud/guide?ref=a1b2c3d4e5f6g7h8
```

文案策略：

### 6.5 首次启动上报

```typescript
// Setup 完成时，后台静默上报
async function trackReferral(): Promise<void> {
  const ref = getRefFromUrl(); // 从 process.argv 或 app.getPath 读取 ?ref=参数
  if (!ref) return;

  const prefs = getPreferences();
  await fetch(`${serverBaseUrl}/referral/track`, {
    method: 'POST',
    body: JSON.stringify({
      ref,
      client_id: prefs.clientId,
      platform: process.platform,
      arch: process.arch,
      version: app.getVersion(),
    }),
  });
}
```

> 客户端不做任何 ref 相关逻辑——归属完全由 Server 端 IP + 时间窗口匹配完成。

### 8.1 数据表变更

**`client_registry` 表**（新增，客户端永久编号）：

> 并发安全：SQLite 单写者 + AUTOINCREMENT，天然无重复编号。

**`referrals` 表**（新增，邀请关系）：

| 字段                    | 类型       | 说明                                   |
| ----------------------- | ---------- | -------------------------------------- |
| `id`                    | int        | 自增主键                               |
| `inviter_client_id`     | string(32) | 邀请者 clientId（完整 16 位 hex）      |

| `arch`                  | string(10) | 被邀请者架构                           |

**`page_events` 表**（修改，增加 ref 字段）：

| 变更                     | 说明                                                |
| ------------------------ | --------------------------------------------------- |
| `+ ref` VARCHAR(32) NULL | 邀请者 clientId。指南页带 `?ref=` 时写入，否则 NULL |

> 不新建 `shortlink_clicks` 表——在现有 `page_events` 加一个 nullable 的 `ref` 字段即可。带 ref 就填，不带就留空。少一张表，少一套维护。

## 9. 关键决策

| #   | 决策                             | 理由                                                          |
| --- | -------------------------------- | ------------------------------------------------------------- |
| 1   | 不做邀请码输入框                 | 增加用户操作步骤，降低转化率                                  |

| 6   | Server 端 IP + 时间窗口匹配归属  | 客户端无法读取网页 ?ref= 参数，纯 Server 端推断，客户端零改动 |
| 7   | 30 天活跃用户做社区计数          | 比全量计数更真实，卸载用户自然淡出                            |
